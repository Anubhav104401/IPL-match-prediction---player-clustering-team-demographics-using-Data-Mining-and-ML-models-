Section 01The project in plain English

1.1What problem is being solved

The Indian Premier League is a professional Twenty20 cricket competition. Since 2008 it has produced a large, public, well-recorded body of data: who played whom, where, who won, and — at the finest level — what happened on every single ball bowled.

That raw record is almost useless to a human being. 260,920 rows describing individual deliveries does not tell you who the best all-rounder is, which players are tactically similar, or whether winning the toss matters. Getting from "here are 260,920 rows" to "here is something a person can act on" is the entire problem this project solves.

It does that in four moves, and each move is a different discipline:

  1. Summarise. Turn 260,920 ball-by-ball rows into one row per player, with meaningful totals — runs, strike rate, wickets, economy. This is feature engineering.
  2. Group. Find natural clusters of players who behave similarly, without being told in advance what the groups are. This is unsupervised learning.
  3. Predict. Learn from past results which side is likely to win a given fixture. This is supervised learning.
  4. Organise. Restructure the data into a database shaped for fast analytical questions. This is data warehousing.

A fifth move sits on top of all of it: a web interface that makes the four results explorable by someone who will never open a Python file. That is what most of this manual is about, because it is the part you are most likely to want to change.

1.3What "data mining" actually means here

"Data mining" sounds like searching for something hidden. In practice it is a specific academic discipline with a standard shape, and this project follows that shape deliberately, because it is a Data Warehousing & Data Mining coursework project. The standard shape is:

SelectionChoose which raw data to work with. Here: two CSV files.
Pre-processingCheck it loads, check the columns exist, handle missing values.
TransformationBuild features — derived numbers that describe each entity usefully.
MiningApply algorithms: clustering to find groups, classification to predict labels.
InterpretationTurn model output into something a person understands — plots, tables, a dashboard.

Every one of those five stages exists as its own file in this project. That is not an accident; it is the structure the discipline expects, and it is why the code is split the way it is.

1.4The one-paragraph version

If you only read one paragraph

Two CSV files describing seventeen seasons of IPL cricket are read by a five-stage Python pipeline. The pipeline computes per-player statistics, groups players into behavioural archetypes using K-Means clustering, trains a gradient-boosting classifier to predict match winners, and loads everything into a SQLite star-schema warehouse. A separate Streamlit web application then reads those outputs and presents them as five interactive pages. The pipeline runs once and writes files to disk; the web app runs continuously and reads them. They never talk to each other directly.

2.3Two programs, not one

This is the single most important structural fact about the project, and the thing most people misunderstand first.

The pipeline and the web app are separate programs

The pipeline

You run python main.py. It works for 30–90 seconds, writes files, and exits. It has no network connection, no port, and no user interface beyond text printed to the terminal.

The web app

You run streamlit run app.py. It starts a web server, holds a port open, and keeps running until you stop it. It only reads files; it never writes any.

How they connect

Only through the filesystem. The pipeline writes .csv and .db files; the app reads them. If you never run the pipeline, the app still starts — it just shows "missing" states.

Careful

Because the connection is files on disk, the web app shows whatever the pipeline produced last time it ran. Editing feature_engineering.py changes nothing in the interface until you re-run python main.py and then restart the app so its caches clear.

There is one exception, and it matters for §8: the match-prediction page trains its own model inside the web app, at the moment you press the button. It does not read a saved model file. That is why the first prediction takes a few seconds and every one after it is instant — see §7.8.

3.3The grain question

"Grain" means: what does one row represent? Getting this right is the foundation of everything downstream, and the two source files have deliberately different grains.

deliveries.csvGrain = one ball. Finest possible. Good for computing anything about individuals.
matches.csvGrain = one match. Good for anything about fixtures and outcomes.
enriched_player_stats.csvGrain = one player. Produced by collapsing deliveries.
enriched_match_features.csvGrain = one match. Produced by widening matches.
fact_matchesGrain = one match. The warehouse's declared grain.

Collapsing from a finer grain to a coarser one is called aggregation, and it is the single most common operation in the pipeline. In pandas it is written dataframe.groupby('batter').agg(...): "gather all rows that share a batter name, then compute one number per group".

Section 04The pipeline, file by file

4.1main.py — the orchestrator

main.py205 lines · runs everything

This file does no analysis itself. Its entire job is to call the other five in the right order, catch any that fail, and print a report at the end.

The core of it is a list of five tuples — a tuple being an ordered pair — where each pairs a name with a function to call:

steps = [
    ('preprocessing', step_preprocessing),
    ('feature_engineering', step_feature_engineering),
    ('clustering', step_clustering),
    ('classification', step_classification),
    ('datawarehouse', step_datawarehouse),
]

for step_name, step_func in steps:
    try:
        result = step_func()
        results[step_name] = result
    except Exception as e:
        print(f"\n[✗] Step '{step_name}' FAILED: {e}")
        traceback.print_exc()
        print(f"    Continuing to next step...\n")

The try / except block means: attempt the step; if it raises an error, print the error and carry on to the next one instead of stopping. That is a deliberate choice with a real trade-off.

Continue on failure, or stop on failure?

Chosen: continue

One broken stage still lets you see the others. Useful for coursework, where a partial run is better than nothing.

Alternative: fail fast

Stop at the first error. Safer, because later stages read earlier stages' output — if feature engineering fails, clustering will read a stale file from a previous run and silently produce out-of-date results.

Careful

Because stages continue after a failure, a failed feature-engineering step is followed by a clustering step that reads yesterday's enriched_player_stats.csv and reports success. Always read the terminal output for [✗] markers rather than trusting the final summary.

The order of the five is not arbitrary — each depends on the previous one's output:

1 preprocessingreads the two source CSVs. Depends on nothing.
2 feature_engineeringreads the two source CSVs, writes two enriched CSVs.
3 clusteringreads enriched_player_stats.csv. Fails if step 2 did.
4 classificationreads enriched_match_features.csv. Fails if step 2 did.
5 datawarehousereads the source CSVs and the outputs of 2 and 3.

Why so small?

In the standard data-mining pipeline, "pre-processing" means cleaning: removing duplicates, filling missing values, correcting types. Here almost none of that is needed at this stage, because the source data is already clean and because the cleaning that is required (dropping matches with no winner, filtering low-exposure players) is specific to each downstream task and is done there instead. That is a defensible choice — cleaning too early throws away rows a later stage might have wanted.

4.3feature_engineering.py — where the numbers come from

feature_engineering.py352 lines · the most important pipeline file

A feature is a number that describes something in a way an algorithm can use. Raw data rarely contains features directly; you compute them. This file computes every feature the rest of the project uses.

compute_batting_stats() L33

Collapses 260,920 delivery rows into one row per batter:

batting = deliveries.groupby('batter').agg(
    total_runs=('batsman_runs', 'sum'),
    balls_faced=('ball', 'count'),
    fours=('batsman_runs', lambda x: (x == 4).sum()),
    sixes=('batsman_runs', lambda x: (x == 6).sum()),
    dot_balls=('batsman_runs', lambda x: (x == 0).sum()),
    innings_played=('match_id', 'nunique'),
).reset_index()

Reading that line by line: group all rows by the batter's name; within each group, sum batsman_runs to get career runs; count rows to get balls faced; count how many of those rows had exactly 4 runs to get boundaries; count distinct match_id values to get innings played. A lambda is just an unnamed one-line function — lambda x: (x == 4).sum() means "given a column, count how many entries equal 4".

Three derived rates follow. Each guards against dividing by zero using np.where(condition, value_if_true, value_if_false):

strike_rateruns ÷ balls × 100. Runs per hundred balls. The standard measure of scoring speed in T20.
dot_ball_pctdot balls ÷ balls × 100. Percentage of balls that produced nothing — a pressure measure.
batting_averageruns ÷ dismissals. Runs scored per time out. If never dismissed, the total runs are used instead.

Dismissals are counted from a different column — player_dismissed — because is_wicket marks the ball, not the person. The code prefers player_dismissed and only falls back to is_wicket if that column is absent L63–L79.

Finally, a filter L89:

batting = batting[batting['balls_faced'] > 50].copy()

Why drop players with 50 balls or fewer?

Chosen: a 50-ball floor

Rate statistics are meaningless on tiny samples. A tail-ender who faced 3 balls and hit a six has a strike rate of 200 — better than every great batter in history. Excluding them keeps the clustering honest.

If the filter were removed

Hundreds of bowlers with a handful of innings would enter the dataset with absurd rates and dominate the extremes of the PCA plot. Clustering would split on noise, and the archetypes would become meaningless.

Cost of the choice

Genuine specialist bowlers who rarely bat are excluded from batting statistics. This is partly why the final clustering only finds two groups — see §5.4.

compute_bowling_stats() L99

The same shape, grouped by bowler instead. Note that runs conceded uses total_runs, not batsman_runs — a bowler is charged for the wides and no-balls they bowl, which is correct cricket accounting.

economy_rateruns conceded ÷ overs bowled, where overs = balls ÷ 6. Runs given away per over. Lower is better — the only metric in the project where that is true.
bowling_strike_rateballs bowled ÷ wickets. Balls needed per wicket. Also lower-is-better. Set to NaN (undefined) for bowlers with no wickets, rather than 0, because 0 would falsely read as "perfect".

Filter here is 60 balls — ten overs L143.

compute_allrounder_score() L152

This is a composite index invented for this project — it is not a standard cricket statistic. It combines batting and bowling into one 0–100 number so that players can be ranked on overall contribution.

# Batting component
bat_raw = df['batting_average'] * df['strike_rate']
df['bat_component'] = (bat_raw - bat_min) / (bat_max - bat_min + 1e-9)

# Bowling component
bowl_raw = np.where(has_bowling, df['wickets_taken'] / df['economy_rate'], 0.0)
df['bowl_component'] = (bowl_raw - bowl_min) / (bowl_max - bowl_min + 1e-9)

df['all_rounder_score'] = ((df['bat_component'] + df['bowl_component']) / 2.0 * 100).round(2)

Three ideas are stacked here:

  1. Multiply to reward both. average × strike_rate is high only if a player scores a lot and scores quickly. Adding them would let one compensate for the other; multiplying demands both.
  2. Divide to invert. wickets ÷ economy rewards taking wickets and penalises leaking runs, because economy is in the denominator and lower economy is better.
  3. Min-max normalise. (x − min) ÷ (max − min) rescales any range to 0–1 so the two components are comparable. The + 1e-9 — a tiny number — prevents division by zero if every player had an identical score.

Equal weighting of batting and bowling

Chosen: 50/50

(bat + bowl) / 2. Defensible, transparent, and requires no justification of arbitrary weights.

Alternative: weight by impact

In T20, a wicket is worth roughly 20–25 runs. Weighting the bowling component higher would reflect that, but any specific weight is a judgement call that would need defending.

Consequence

Pure batsmen score at most 50 (bowling component = 0), so the top of the index is dominated by genuine all-rounders. That is the intended behaviour, and it is why the metric is named as it is.

Careful — min-max is sample-dependent

Because normalisation uses the minimum and maximum of this dataset, adding a new season changes every player's score, even players whose own numbers did not change. The index is a ranking within a fixed population, not an absolute measure.

compute_venue_stats() L191

Two outputs. First, average total runs per match at each ground, computed by joining every delivery to its match's venue and summing. Second, each team's win percentage at each ground.

compute_head_to_head() L234

For every pair of teams that has ever met, what share of those meetings each side won. The important trick is at L245:

pair = tuple(sorted([t1, t2]))

Sorting the two names alphabetically before using them as a key means "Mumbai vs Chennai" and "Chennai vs Mumbai" produce the same key. Without this, the same fixture would be counted as two unrelated rivalries depending on which side was listed first in the source data.

compute_team_form() L275

A rolling win rate over each team's previous five matches — a numeric proxy for "are they in form right now?" The critical line is L293:

team_matches['form_win_pct'] = (
    team_matches['team_won']
    .rolling(window=5, min_periods=1)
    .mean()
    .shift(1)              # ← don't include current match
    .fillna(0.5) * 100
)
Why .shift(1) is the most important call in the file

.rolling(5).mean() averages the last five results including the current one. Since the current result is the thing being predicted, including it would leak the answer into the question. .shift(1) moves the window back by one match so form is computed strictly from the past. Without that single call the classifier would appear far more accurate than it is — exactly the failure documented in §5.7, which happened elsewhere in the same file.

build_enriched_match_features() L308

Joins all of the above onto the match table, producing the 14-column file the classifier trains on. The final line L349 is the one that causes trouble:

df['toss_winner_won'] = (df['toss_winner'] == df['winner']).astype(int)

This computes "did the toss winner also win the match". As a descriptive statistic it is perfectly reasonable. As a model feature it is fatal, because winner is the thing being predicted. See §5.7 for the full story.

4.4clustering.py — finding player archetypes

Unsupervised means nobody tells the algorithm what the right answer is. There are no labels saying "this player is an all-rounder". The algorithm is given 382 players described by 11 numbers each, and asked to find groups of players whose numbers are similar. The names attached to those groups afterwards are the project's interpretation, not the algorithm's output.

Why only two archetypes?

k = 2 wins, and the result is 62 "Elite All-Rounder" and 320 "Key Bowler". That is a thin outcome for a page about archetypes, and it is a real limitation of the current data, not a bug. The 50-ball batting filter admits many bowlers who bat occasionally, so the dominant structure in the feature space is simply "bowls a lot" versus "does both". Forcing k = 5 would produce richer labels at the cost of weaker statistical support — the honest reading is that this feature set supports two groups.

You can change this

Section 05The machine learning, and why these choices

This section answers, for each algorithm: what it is, why it was chosen, what the alternatives were, and what would have been different had one of those been used instead.

5.1Why the project uses two kinds of learning

Machine learning splits into two broad families, and this project deliberately uses one of each — because the coursework asks for both, and because the two answer genuinely different questions.

Supervised versus unsupervised

Unsupervised — clustering

You have data but no answers. "Here are 382 players; find the natural groups." There is no correct answer to check against, so quality is judged by internal measures like silhouette score. Used here for player and team archetypes.

Supervised — classification

You have data and answers for past examples. "Here are 1,072 matches and who won each; predict the winner of a new one." Quality is judged by testing on examples the model was not trained on. Used here for match prediction.

Why not just one

Clustering cannot predict a winner — it has no notion of a target. Classification cannot discover archetypes — it can only learn labels you already have. They are not substitutes.

5.2Standardisation — the step everyone skips and shouldn't

StandardScaler appears before every clustering and classification step. It transforms each column so it has a mean of 0 and a standard deviation of 1:

z = (x - mean) / standard_deviation

The resulting numbers are called z-scores: a value of +2 means "two standard deviations above average for this column".

Why it is mandatory here

Look at the raw ranges in this dataset:

FeatureTypical rangeSpread
total_runs50 – 8,014~8,000
strike_rate60 – 200~140
economy_rate5 – 12~7

K-Means groups points by straight-line distance. Distance is dominated by whichever number is biggest. Without scaling, total_runs — with a spread a thousand times larger than economy_rate — would decide the clusters almost single-handedly, and the algorithm would effectively be sorting players by career runs while pretending to consider eleven features.

Which scaler

Chosen: StandardScaler

Subtract mean, divide by standard deviation. The standard choice, and the one PCA assumes — PCA finds directions of maximum variance, which is only meaningful if variance is comparable across columns.

Alternative: MinMaxScaler

Squeezes everything into 0–1. Simple, but a single outlier — one player with 8,014 runs — compresses everyone else into a narrow band near zero. Worse here, because cricket statistics are heavily skewed.

Alternative: RobustScaler

Uses median and interquartile range, so outliers barely move the scale. Arguably the best fit for this heavily-skewed data, and a defensible improvement — it would pull the elite outliers back toward the cluster structure rather than letting them stretch it.

Careful — fit on train, transform on test

In classification.py L86 the scaler is fitted on the entire dataset before the train/test split. Strictly this leaks a small amount of information — the test set's mean and standard deviation influence the training data's scaling. The effect is minor for a scaler, but the textbook-correct order is: split first, then fit_transform on train and transform only on test.

5.3PCA — turning eleven dimensions into two

Principal Component Analysis solves a display problem. Each player is described by 11 numbers, which means each player is a point in 11-dimensional space. Nobody can look at 11 dimensions.

PCA finds the two directions through that 11-dimensional cloud along which the points are most spread out, and projects everything onto them. Those two directions become the x and y axes of the scatter plot on the Players page.

The intuition

Imagine photographing a swarm of bees. The swarm is three-dimensional but the photograph is flat. Some camera angles show the swarm's shape clearly; others flatten it into a blob. PCA automatically finds the angle that preserves the most visible spread — and then tells you what fraction of the real structure survived.

Measured on this dataset:

Component 1explains 44.0% of the total variance
Component 2explains 23.0%
Together67.0% — the number shown on the Players page stat tile

That means a third of the structure is invisible in the plot. Two players who appear to overlap on screen may be far apart in the full space. The interface says this explicitly in the insight box under the chart, which is written at views/players.py L129.

PCA versus the alternatives

Chosen: PCA

Linear, deterministic, fast, and — crucially — it reports how much information it kept. Axes have a consistent meaning across runs, and distances in the plot approximate distances in the original space.

Alternative: t-SNE

Usually produces prettier, more obviously separated blobs. But it is stochastic (different every run), gives no variance-explained figure, and — the deal-breaker — distances between clusters in a t-SNE plot are meaningless. Two clusters far apart may not be far apart. Fine for exploration, wrong for a report.

Alternative: UMAP

Faster than t-SNE and preserves more global structure, but it is a third-party dependency and carries the same interpretability caveat. Would have made the scatter plot look better and mean less.

A subtlety worth knowing

The clustering itself runs on the full 11-dimensional scaled data (clustering.py L146 passes X_scaled, not X_pca). PCA is used only to draw the result. This is the right way round: clustering on the 2-D projection would throw away a third of the information before deciding anything. It also explains why cluster boundaries in the plot sometimes look ragged — you are seeing a 2-D shadow of an 11-D partition.

5.4K-Means, the elbow method, and silhouette score

How K-Means works

  1. Place k centres at random in the feature space.
  2. Assign every player to the nearest centre.
  3. Move each centre to the average position of the players assigned to it.
  4. Repeat steps 2 and 3 until nothing moves any more.

The word "means" is literal: each cluster centre is the mean of its members. The parameter n_init=10 in the code runs the whole procedure ten times from ten different random starts and keeps the best, because a bad starting position can trap the algorithm in a poor solution.

Choosing k — two methods, one answer

InertiaTotal squared distance from each point to its own cluster centre. Always decreases as k rises, so it cannot be maximised — you look for the "elbow" where the improvement flattens.
SilhouetteFor each point: how close it is to its own cluster versus the nearest other cluster, scaled to −1…+1. Averaged over all points. Has a true maximum, so it can be optimised directly.

Reading the measured table in §4.4: inertia drops steeply from k=2 to k=4 then gently — there is no dramatic elbow. Silhouette peaks clearly at k=2 (0.383) and never recovers. The code therefore selects by silhouette.

How good is 0.383?

Silhouette runs −1 to +1. Above 0.7 is strong structure; 0.5–0.7 is reasonable; 0.25–0.5 is weak but real; below 0.25 means the clusters are largely arbitrary. At 0.383 this dataset has weak-to-moderate structure — the groups exist but are not sharply separated. That is an honest result for cricket statistics, where players form a continuum rather than distinct types.

K-Means versus the alternatives

Chosen: K-Means

Fast, deterministic given a seed, produces exactly k groups so the output is predictable, and every cluster has an interpretable centre you can describe. That last point matters: the labelling step needs a profile per cluster.

Alternative: Hierarchical / Agglomerative

Builds a tree of nested groupings you can cut at any level, and produces a dendrogram — genuinely informative for a report. Cost: O(n²) memory, and no cluster centres to describe. At 382 players it would have run fine and would have been a reasonable second choice.

Alternative: Gaussian Mixture Model

Gives each player a probability of belonging to each cluster rather than a hard assignment — arguably truer to cricket, where a player can be 70% all-rounder. Also handles elongated, non-spherical clusters that K-Means cannot. The cost is a harder story to tell and no single label per player.

K-Means' built-in assumption

K-Means implicitly assumes clusters are roughly spherical and similarly sized, because it assigns by straight-line distance to a centre. Cricket archetypes are almost certainly not spherical — the "all-rounder" region is a long ridge, not a ball. This is a real limitation of the choice, and part of why the silhouette score is only moderate.

5.5DBSCAN — the alternative that was tried and rejected

DBSCAN groups points by density rather than distance to a centre. It has two parameters: eps (how close counts as neighbouring) and min_samples (how many neighbours make a dense region). Points in no dense region are labelled noise, as cluster −1.

The code auto-tunes eps using a nearest-neighbour heuristic clustering.py L157:

nn = NearestNeighbors(n_neighbors=5)
distances, _ = nn.kneighbors(X_scaled)
sorted_distances = np.sort(distances[:, -1])
eps = np.percentile(sorted_distances, 90)

Translated: for every player, measure the distance to their 5th-nearest neighbour; sort those distances; take the 90th percentile as the neighbourhood radius.

Why DBSCAN loses here

What it is good at

Finding oddly-shaped clusters, and explicitly identifying outliers instead of forcing every point into a group. Genuinely better than K-Means for spatial data.

Why it fails on this data

In 11 dimensions, distances between points become uniformly large — the "curse of dimensionality". Density stops being a useful signal, and DBSCAN tends to return either one giant cluster or almost everything as noise.

The decision

Both are run, both silhouette scores are printed side by side, and K-Means is selected at L324. Running the loser and reporting the comparison is better practice than quietly picking one.

5.6The four classifiers

Four algorithms from four different families are trained on identical data and compared. Each has a different inductive bias — a different assumption about what patterns look like.

Random Forest

Builds 200 decision trees, each on a random subset of rows and columns, then takes a majority vote. A single decision tree is a flowchart of yes/no questions; it memorises training data badly. Averaging many decorrelated trees cancels out their individual mistakes. Bagging — trees built in parallel and independently.

Gradient Boosting

Also builds many trees, but sequentially: each new tree is trained specifically on the errors the previous ones made. Boosting — trees built in series, each correcting its predecessors. Usually more accurate than a forest on tabular data, and more prone to overfitting, which is exactly what happened here (§5.8).

Logistic Regression

Fits a weighted sum of the inputs and squashes it into a probability. Assumes the relationship is essentially linear. Its value in the comparison is as a baseline: if a complex model cannot beat it, the complexity is not earning its keep.

Support Vector Machine

Finds the boundary that separates classes with the widest possible margin. The kernel='rbf' setting lets it draw curved boundaries. Powerful, but scales poorly — its training time grows roughly with the square of the number of rows — and it does not produce probabilities natively, which is why probability=True is set; that flag makes scikit-learn run an extra internal calibration step.

Because there is no universally best algorithm — a result formalised as the "no free lunch" theorem. Which model wins depends on the shape of the data, and the only way to find out is to try them. Reporting all four, with cross-validated means and standard deviations, is the honest form of this exercise; reporting only the winner hides how close the race was.

5.7The leakage story — the most important thing in this document

Common misconception

"The model predicts IPL match winners with 96–97% accuracy." It does not. That number is an artefact of a broken evaluation, and understanding why is more educational than any correct result in this project.

What happened

The feature list in classification.py L65 includes toss_winner_won. That column is created in feature_engineering.py L349 as:

df['toss_winner_won'] = (df['toss_winner'] == df['winner']).astype(int)

Read that carefully. The column is defined in terms of winner — the very thing the model is asked to predict. The model is also given toss_winner as a one-hot column. So the model receives, in effect:

Input A"The toss was won by Chennai."
Input B"The toss winner went on to win the match."
Question"Who won the match?"

Any model can answer that by combining A and B. It is not predicting; it is reading the answer off the exam paper. This is called target leakage.

The measurement

Both configurations were trained and tested on identical splits of the same data. The only difference is whether that one column is present:

Feature setHeld-out accuracy
With toss_winner_won96.3%
Without it54.4%

A single column accounts for 42 percentage points. It was also verified directly that the column is exactly equal to (toss_winner == winner) for every row — not correlated with it, identical to it.

The second, worse problem

Even setting accuracy aside, the feature is unusable at prediction time. You are asked to predict a match that has not been played. The toss winner is known — it is one of the two sides — but whether they went on to win is precisely what you are trying to work out. The original dashboard code handled this by setting the value to 1 whenever the toss winner was one of the two teams, which is always. So at prediction time the model was told, every single time, "the toss winner won this match", and it faithfully predicted the toss winner with near-100% confidence.

Where things stand now

The interface's model (ui/model.py L28) excludes the feature and blocks it through an explicit LEAKING tuple at L35, so it cannot be reintroduced by accident. The pipeline's model (classification.py L65) still contains it — that file was left untouched deliberately, and the discrepancy is documented in the README. If you want the pipeline's reported accuracy to be meaningful, delete 'toss_winner_won' from that list and re-run.

How to spot leakage in general

  • Accuracy that seems too good for the problem. Match prediction in T20 cricket is genuinely hard; bookmakers do not achieve 96%.
  • A feature whose definition mentions the target.
  • A feature you could not possibly know at the moment of prediction.
  • A single feature dominating importance rankings.

5.8Calibration — when 100% confident means nothing

Removing the leak fixed the accuracy but exposed a second problem: the model was still returning absurd confidence. It would say "100.0%" while being right barely half the time.

This is a calibration failure. A well-calibrated model that says "70% confident" should be right about 70% of the time. The original configuration was systematically overconfident.

Why it happened

Gradient boosting with max_depth=5 and 150 trees, trained on ~857 rows with 200+ mostly-zero columns, has more than enough capacity to memorise the training set. Deep trees carve the space into tiny regions each containing a handful of matches, and the probability in each region collapses to 0 or 1.

The fix and the measurement

ConfigurationAccuracyLog-lossPredictions above 0.9 confidence
n=150, depth=5, lr=0.156.3%2.3877%
n=80, depth=2, lr=0.05, subsample=0.761.9%0.747%

What log-loss measures, and why it is the honest metric here

Accuracy only asks "was the top choice right". Log-loss also asks "how confident were you, and were you entitled to be" — it punishes confident errors far more than hesitant ones. Dropping from 2.38 to 0.74 means the model's stated probabilities became roughly three times more trustworthy. Accuracy improving at the same time is the giveaway that the original model was not merely overconfident but genuinely overfitted.

The alternative that was not taken

Instead of regularising, one could keep the original model and wrap it in CalibratedClassifierCV, which learns a correction mapping raw scores to honest probabilities. That would have fixed calibration but not the underlying overfitting, and it costs an extra layer of cross-validated training on every run. Regularising fixed both problems at once and made the model faster.

5.9SHAP — explaining what the model learned

A gradient-boosting model with 150 trees is not readable. SHAP (SHapley Additive exPlanations) answers "how much did each feature contribute to this particular prediction?" using a concept borrowed from cooperative game theory: Shapley values, which fairly divide a payout among players who contributed unequally. Here the "payout" is the prediction and the "players" are the features.

The code uses TreeExplainer for tree models classification.py L207, which is exact and fast for trees, and falls back to KernelExplainer for the others, which is model-agnostic but far slower — hence the sampling to 50 rows.

SHAP versus simpler importance measures

Chosen: SHAP

Gives per-prediction explanations, has a sound theoretical basis, and works across model types. Also produces the global ranking used in the saved plot.

Alternative: Gini importance

model.feature_importances_ — free, instant, already computed during training. But it is biased toward high-cardinality features, which matters enormously here where venue expands into 58 columns. The code keeps it as a fallback at L246.

Alternative: Permutation importance

Shuffle one column and measure how much accuracy drops. Intuitive and unbiased, but only global — it cannot explain an individual prediction, and it is slow on 200+ columns.

What the SHAP plot currently shows

Because the pipeline model still includes the leaking feature, toss_winner_won dominates its SHAP ranking. That plot is, in effect, a picture of the leak. It is worth looking at for exactly that reason — and worth regenerating after removing the feature, at which point venue and form should rise to the top.

Section 06The data warehouse

6.1OLTP versus OLAP — why a second copy of the data exists

A reasonable question: the data is already in CSV files, so why load it into a database as well? The answer is that databases come in two shapes, optimised for opposite jobs.

Two database philosophies

OLTP — transactional

Online Transaction Processing. Optimised for many small reads and writes: "record this booking", "update this address". Heavily normalised to avoid duplication. What a booking site runs on.

OLAP — analytical

Online Analytical Processing. Optimised for few enormous read-only queries: "average margin by venue by season". Deliberately de-normalised, duplicating descriptive text to avoid joins. What this project builds.

Why not just use the CSVs

Answering "average result margin per venue, seasons with at least five matches" over CSVs means loading 27 MB into memory and grouping in pandas every time. The warehouse answers it in SQL over 1,095 narrow rows, and the question is expressible declaratively.

6.2Star schema versus snowflake

A star schema has one central fact table surrounded by dimension tables. The fact table holds measurements and foreign keys; the dimensions hold descriptive attributes. Drawn out, it looks like a star — hence the name.

Fact tableNumerous, narrow, numeric. One row per event. Here: fact_matches, 1,095 rows, 8 columns.
Dimension tableFew rows, wide, descriptive. One row per thing. Here: dim_team (19), dim_venue (58), dim_player (382), dim_date (823).
GrainWhat one fact row means. Declared here as: one completed match.

Star versus snowflake

Chosen: star

Dimensions are flat and denormalised. dim_venue holds both venue name and city in the same row, even though that duplicates the city text across venues. Every query is one join deep.

Alternative: snowflake

Normalise the dimensions further — split city into its own dim_city that dim_venue points at. Saves a trivial amount of space and costs an extra join on every city-based query.

Why star wins here

Storage is free at this scale (the whole database is 131 KB). Query simplicity is not. The star schema is also the form the coursework expects and the form most BI tools assume.

6.4The five OLAP queries

Each demonstrates a different SQL capability. They appear both in the pipeline's terminal output and, in slightly adapted form, on the Warehouse page of the interface.

Q1 — Top venues by average margin

SELECT v.venue_name AS Venue,
       ROUND(AVG(f.result_margin), 2) AS Avg_Margin,
       COUNT(*) AS Matches
FROM fact_matches f
JOIN dim_venue v ON f.venue_key = v.venue_key
WHERE f.result_margin > 0
GROUP BY v.venue_name
HAVING Matches >= 5
ORDER BY Avg_Margin DESC
LIMIT 8;

Demonstrates: the fact-to-dimension join, aggregation, and the WHERE/HAVING distinction — WHERE filters individual rows before grouping, HAVING filters the groups afterwards. You cannot use WHERE on COUNT(*) because the count does not exist until grouping has happened.

Q2 — Toss decisions per season

SELECT d.season AS Season, f.toss_decision AS Decision, COUNT(*) AS Matches
FROM fact_matches f
JOIN dim_date d ON f.date_key = d.date_key
WHERE f.toss_decision IS NOT NULL
GROUP BY d.season, f.toss_decision
ORDER BY d.season;

Demonstrates: grouping on two dimensions at once — a cross-tabulation, the basic OLAP operation.

Q3 — Most dominant team per season

WITH team_season AS (
    SELECT d.season, t.team_name, COUNT(*) AS wins
    FROM fact_matches f
    JOIN dim_date d ON f.date_key = d.date_key
    JOIN dim_team t ON f.winner_key = t.team_key
    GROUP BY d.season, t.team_name
),
ranked AS (
    SELECT season, team_name, wins,
           ROW_NUMBER() OVER (PARTITION BY season ORDER BY wins DESC) AS rn
    FROM team_season
)
SELECT season AS Season, team_name AS Team, wins AS Wins
FROM ranked WHERE rn = 1 ORDER BY season;

Demonstrates: the most advanced SQL in the project. WITH … AS defines a Common Table Expression — a named temporary result you can query as if it were a table. ROW_NUMBER() OVER (PARTITION BY season ORDER BY wins DESC) is a window function: it numbers rows 1, 2, 3… restarting the count for each season, ordered by wins. Filtering to rn = 1 then keeps only the top team per season. Doing this without window functions requires a correlated subquery and is considerably uglier.

Q4 — Top all-rounders

SELECT player_name AS Player, total_runs AS Runs,
       ROUND(strike_rate, 2) AS SR, wickets AS Wickets,
       ROUND(all_rounder_score, 2) AS AR_Score, cluster_label AS Cluster
FROM dim_player
WHERE all_rounder_score > 0
ORDER BY all_rounder_score DESC
LIMIT 12;

Demonstrates: that a dimension table can be queried alone. Note it returns the cluster label — the machine-learning output has been loaded into the warehouse and is now queryable with SQL alongside everything else. That closing of the loop is the point of the exercise.

Q5 — Cluster-wise averages

SELECT cluster_label AS Cluster, COUNT(*) AS Players,
       ROUND(AVG(total_runs), 1) AS Avg_Runs,
       ROUND(AVG(strike_rate), 2) AS Avg_SR,
       ROUND(AVG(wickets), 1) AS Avg_Wickets,
       ROUND(AVG(all_rounder_score), 2) AS Avg_AR
FROM dim_player
WHERE cluster_label != 'Unknown'
GROUP BY cluster_label
ORDER BY Avg_AR DESC;

Demonstrates: aggregating by a machine-learning-produced category. This is the query that validates the clustering — if the archetypes were meaningless, their averages would look identical.

Why SQLite and not PostgreSQL or MySQL

SQLite is a single file with no server, no configuration, no user accounts and no network port. It ships inside Python's standard library, so there is nothing to install. For a 131 KB read-mostly analytical database used by one application, a client-server database would add operational complexity and buy nothing. The trade-off — weak concurrent writes and limited data types — is irrelevant here because the warehouse is written once by one process.

7.1Architecture — and why it is split into eleven files

The original dashboard was one 600-line file containing data loading, chart building, layout, CSS and model training all interleaved. It has been split into three layers with a strict rule: dependencies only point downward.

Why split it at all

Chosen: three layers

A colour is defined once, in ui/tokens.py. Changing it changes the CSS, the charts and the custom SVG together, because all three read the same source.

The single-file alternative

Simpler to open, but a colour appears a dozen times as a literal. Change one and the chart no longer matches the card behind it. This is exactly the drift the split prevents.

The cost

More files to navigate, and you have to know which layer a change belongs in. The lookup table in §7.11 exists to remove that cost.

Common misconception

"You inject CSS in Streamlit with st.markdown('<style>…', unsafe_allow_html=True)." That is the widely-copied recipe, and in Streamlit 1.56 it silently fails for a stylesheet of this shape. The HTML sanitiser rejects the whole <style> block — no error, no warning, the CSS simply never arrives. The symptom is subtle: your custom classes appear in the DOM but every var(--…) resolves to nothing, so gradient text turns invisible and custom fonts fall back. Passing the sheet through a component's css= parameter with isolate_styles=False delivers it verbatim to the document.

Section 08Ports, servers and what actually travels over the wire

Read this first

If you have learned web development from a typical tutorial, you are expecting a particular architecture: a browser builds a JSON object, sends it by HTTP POST to an API endpoint, middleware parses and validates it, a route handler runs, and JSON comes back. This project has none of that. There is no middleware layer, no REST API, no JSON request body, no endpoint per action, and no routing table mapping URLs to handler functions.

That is not a gap in the project. Streamlit is built on a fundamentally different model, and the rest of this section explains what it actually does instead — with the real port numbers, the real endpoint paths, and the real message format, all read from the installed framework source.

8.1What "streamlit run app.py" actually does

  1. Python starts and imports the streamlit package.
  2. Configuration is read from .streamlit/config.toml, then overridden by any command-line flags such as --server.port.
  3. A Tornado web server starts. Tornado is a Python web server and asynchronous networking library. It binds to the configured port and begins listening.
  4. Nothing runs your script yet. app.py has not been executed. The server is simply waiting.
  5. A browser connects. It requests / and receives a small HTML page plus a JavaScript bundle. That bundle is the real user interface — a React application.
  6. The JavaScript opens a WebSocket back to the server at /_stcore/stream. This connection stays open for the entire session.
  7. Now your script runs. The server creates a session, executes app.py from the first line to the last, and streams the resulting user interface elements down the open socket as they are produced.
  8. The script finishes and exits. The interface remains on screen. When you interact with a widget, the script is executed again from the top — see §8.5.

8.2The port, and the two processes

Default port8501. Confirmed from the framework's own config table: server.port default=8501.
Default addressNone, which means bind to all interfaces — the app is reachable from other machines on the network, not only localhost.
ProtocolPlain HTTP, then an upgrade to WebSocket. No TLS by default.
Overriding itstreamlit run app.py --server.port 8555. This document's screenshots were captured on 8555 to avoid clashing with a running instance.

There is exactly one server process, and it serves both the static assets and the live session. There is no separate frontend server, no reverse proxy, no application server behind a web server. The two "processes" you should think about are:

The two halves of a running app

Server side — Python

Tornado on port 8501. Holds one session per connected browser tab. Runs app.py on demand. Owns the caches, the trained model, and all file access.

Client side — JavaScript

A React application in the browser. Owns the DOM. Renders whatever elements the server sends. Sends widget values back when the user interacts.

What connects them

One long-lived WebSocket. Not request/response — a persistent bidirectional stream. This is the architectural difference that removes the need for middleware.

8.4The WebSocket — and why there is no JSON request

Everything of consequence travels over the single WebSocket at /_stcore/stream. The format is binary Protocol Buffers, not JSON.

Protocol Buffers ("protobuf") is Google's binary serialisation format. You define message shapes in a schema file; a compiler generates code to read and write them; the wire format is compact binary with numbered fields rather than field names. The installed Streamlit package contains 180 generated protobuf files in streamlit/proto/.

From streamlit/web/server/browser_websocket_handler.py:

self.write_message(serialize_forward_msg(msg), binary=True)   # server → browser

binary=True and ParseFromString are the tell. If this were JSON you would see json.dumps and json.loads.

"What algorithm converts plain text into the JSON request format?"

There isn't one, because there is no JSON request. The nearest true answer is: protobuf serialisation, and it is not a text-parsing algorithm at all. A selectbox does not send the text "Chennai Super Kings". It sends int_value = 3 — the index of that option in the list the server sent earlier. The server already knows the list, so it looks up index 3 and gets the string back. Field numbers replace field names, integers replace strings, and the whole message is a compact byte sequence with no delimiters to parse.

"How does it decide which requests are complex and which are normal?"

It doesn't classify requests by complexity, because there is only one kind of request: rerun_script. Every interaction — changing a dropdown, pressing a button, switching pages — sends the same message type with different contents. There is no fast path and no slow path, no routing decision, no dispatcher.

Three real distinctions do exist, and they may be what the question is reaching for:

  • Which widget changed — determined by comparing the incoming widget_states against the previous ones, not by a request type.
  • Which page to run — determined by page_script_hash.
  • Whether work can be skipped — determined by the cache decorators, which compare argument hashes. This is the only real "is this expensive?" decision in the system, and it is made in Python, not on the wire. See §8.8.

8.5The rerun model — the mental model that explains everything

This is the single idea that makes Streamlit make sense.

The rule

Every interaction re-runs the entire script from the first line to the last. Not a callback. Not a handler for that one widget. The whole file, top to bottom, every time.

Change the venue dropdown on the prediction page and the following happens, in order:

  1. The browser sends BackMsg{rerun_script} carrying every widget's current value.
  2. The server begins executing app.py from line 1.
  3. st.set_page_config runs again. theme.inject() runs again. charts.register_template() runs again.
  4. navigation.run() calls prediction.render(), which executes top to bottom.
  5. When execution reaches st.selectbox("Venue", venues), that call returns the value the browser just sent. That is how a stateless re-run appears stateful.
  6. Every element produced is streamed to the browser as a delta in a ForwardMsg.
  7. The React client diffs the new element tree against the old and updates only what changed — so the screen does not flash even though the script ran completely.

Three consequences follow directly, and they explain most of the design decisions in ui/:

Caching is not optionalWithout it, every dropdown change would re-read a 27 MB CSV and retrain the model. The decorators in ui/data.py and ui/model.py are what make the app usable, not an optimisation.
Widgets need stable identityStreamlit identifies a widget by its type, label and position. Two selectboxes with the same label in the same place would collide, which is why every widget in views/prediction.py has an explicit key=.
Ordinary variables do not persistA variable assigned during one run is gone at the next. State lives in three places only: widget values, the caches, and st.session_state.

8.6Where JSON does appear

JSON is not absent — it is just not where a REST-shaped mental model expects it. There are exactly three places:

1. Custom component data — the one this project uses heavily

Every call to ui.markup(...) and every mount of the theme or runtime component goes through this path. From streamlit/components/v2/bidi_component/serialization.py:

if arrow_blobs:
    # We have dataframes, use mixed data serialization
    mixed_proto = MixedDataProto()
    try:
        mixed_proto.json = json.dumps(processed_data)
    except TypeError:
        mixed_proto.json = json.dumps(str(processed_data))
    for ref_id, arrow_bytes in arrow_blobs.items():
        mixed_proto.arrow_blobs[ref_id].data = arrow_bytes
    bidi_component_proto.mixed.CopyFrom(mixed_proto)
else:
    # No dataframes found, use regular JSON serialization
    bidi_component_proto.json = json.dumps(processed_data)

So json.dumps — Python's standard JSON encoder — is the actual answer to "how is the JSON created", and the BidiComponent protobuf message has a json field (field 10) that carries it as a string inside the binary protobuf envelope.

This is the closest thing to a "complex vs normal" decision in the whole system

The code above is a genuine two-way branch, and it is worth reading carefully because it is probably what the question about request complexity was aiming at.

Before serialising, _extract_dataframes_from_dict() walks the top level of the data and asks is_dataframe_like(value) of each entry. If none are found — the normal case, and the only case this project hits, since ui.markup() passes a single HTML string — the payload takes the simple path: one json.dumps into the json field.

If a dataframe is found — the complex case — it takes the mixed path. Each dataframe is serialised to Arrow bytes, hashed with MD5 to produce a content-addressed reference id, stored in a separate arrow_blobs map, and replaced in the JSON by a small placeholder object holding only that id. Two identical dataframes therefore produce the same hash and are transmitted once. The JSON and the binary blobs travel together in a MixedData message and are reunited on the client.

The classification is by content type, not by size or cost — and it happens in Python before anything is sent, not in a middleware layer inspecting an incoming request.

2. WidgetState.json_value

Field 10 of WidgetState. A fallback for widget values with no dedicated typed field. Not used by any widget in this project.

3. Component trigger values

When a custom component sends something back to Python, the payload arrives as a JSON string and is decoded by handle_deserialize(), which falls back to returning the raw string if it is not valid JSON. This project's runtime component never sends anything back, so this path is unused here.

8.7Arrow — how tables travel

Every st.dataframe(...) call in this project sends its table as Apache Arrow IPC bytes, not as JSON rows. From streamlit/dataframe_util.py:

sink = pa.BufferOutputStream()
writer = pa.RecordBatchStreamWriter(sink, table.schema)
writer.write_table(table)
writer.close()
return sink.getvalue().to_pybytes()

Arrow is a columnar in-memory format. Instead of storing row by row — {"player": "V Kohli", "runs": 8014} repeated 382 times, with the key names repeated every row — it stores column by column: all 382 player names contiguously, then all 382 run totals contiguously as a block of integers.

SmallerColumn names appear once in the schema, not once per row. Numbers stay binary rather than becoming decimal text.
FasterThe JavaScript side reads it into typed arrays with no parsing loop.
TypedAn integer column stays integer. JSON would turn it into a number the client has to re-infer.

This is why the sortable, scrollable tables on the Players and Teams pages feel instant despite holding hundreds of rows: the browser receives a typed binary buffer, not a text document to parse.

8.10One full round trip, traced end to end

You are on the prediction page. You change "Away side" from Deccan Chargers to Mumbai Indians and press "Run prediction". Here is every step:

  1. Browser. The React select captures the change. It looks up "Mumbai Indians" in the option list it was given and finds index 4.
  2. Browser. A BackMsg is built with rerun_script set. Inside it, a ClientState containing every widget's value: the away-side selectbox as WidgetState{id: "pred_team2", int_value: 4}, plus the four other dropdowns and the button's trigger_value.
  3. Browser. The message is serialised to binary protobuf and written to the open WebSocket. Roughly a few hundred bytes.
  4. Server. Tornado's BrowserWebSocketHandler.on_message receives the bytes and calls msg.ParseFromString(message).
  5. Server. AppSession.handle_backmsg sees rerun_script and queues a rerun with the new widget state.
  6. Server. The script runner executes app.py from line 1. Page config, theme injection, template registration, logo, navigation table.
  7. Server. theme.inject() emits the 19 KB stylesheet — but its content hash is unchanged, so a ref_hash pointer goes out instead of the payload.
  8. Server. navigation.run() dispatches to prediction.render().
  9. Server. data.load_matches() is called. Its cache key is unchanged, so the cached dataframe is returned in microseconds — no CSV is read.
  10. Server. Execution reaches st.selectbox("Away side", opponents, key="pred_team2"). Streamlit looks up pred_team2 in the incoming widget state, finds int_value: 4, indexes the list, and the call returns the string "Mumbai Indians".
  11. Server. ui.versus(team1, team2, venue) builds an HTML string containing two inline SVG crests. It is passed as data= to the markup component, JSON-encoded with json.dumps into the json field of a BidiComponent protobuf.
  12. Server. The button's trigger_value is true, so ml.train() is called. Its cache key is unchanged from earlier in the session, so the fitted GradientBoostingClassifier is returned instantly — the same object, not a copy.
  13. Server. trained.predict(...) builds a one-row dataframe matching the training columns, calls predict_proba, and renormalises over the two named sides.
  14. Server. ui.verdict() produces the result panel, including an SVG arc whose stroke-dashoffset encodes the confidence percentage.
  15. Server. The probability bar chart is built by Plotly and serialised into a ForwardMsg delta.
  16. Server. A final ForwardMsg{script_finished} is sent.
  17. Browser. Each delta is applied to the React element tree. Unchanged elements are left alone; only the crest, the verdict panel and the chart re-render.
  18. Browser. The runtime component's JavaScript re-runs, finds the new data-count elements in the verdict panel, and animates them.

Total: one binary message up, a stream of binary deltas down, no JSON in the request, no middleware, and no endpoint that corresponds to "predict".

10.3Known weaknesses, stated plainly

  1. The pipeline classifier still leaks. classification.py L65 retains toss_winner_won, so its reported 96.74% is not a real accuracy. The interface model is fixed; this one is not.
  2. Only two archetypes emerge. Silhouette selects k = 2, which makes a page about archetypes thinner than it should be. Richer features — phase-of-innings splits, role in the batting order — would likely support more.
  3. Run-outs are credited to bowlers. Wicket counts are slightly inflated.
  4. The warehouse's season differs from the CSVs'. datawarehouse.py L138 derives season from the calendar year rather than carrying the original label.
  5. The cluster-labelling heuristic is fragile. clustering.py L214 contains conditions that always evaluate true. It works on the current data by luck as much as design.
  6. The scaler is fitted before the train/test split in classification.py L86 — a minor form of leakage.
  7. 62% accuracy is a modest edge. Real but small. T20 cricket is high-variance and no model built on these features will do dramatically better.
  8. The interface is dark-only. There is no light theme, and adding one means rewriting the token file with a second palette.

Section 11Glossary

AggregationCollapsing many rows into fewer by computing a summary per group. groupby(...).sum().
ArrowA columnar binary format for tables. How st.dataframe sends data to the browser.
BoostingBuilding models in sequence, each correcting the previous one's errors.
BaggingBuilding many models in parallel on random subsets and averaging them.
CalibrationWhether a model's stated confidence matches how often it is right.
Cross-validationSplitting data into k parts and training k times so every part serves once as the test set.
CSS custom propertyA named value in a stylesheet, written --name: value and used as var(--name).
Dimension tableIn a warehouse, a small descriptive table — teams, venues, dates.
Fact tableIn a warehouse, the large table of events with measurements and foreign keys.
FeatureA number describing something, used as model input.
Foreign keyA column holding another table's key, linking the two.
GrainWhat one row of a table represents.
HyperparameterA setting you choose before training — tree depth, learning rate — as opposed to something learned.
InertiaTotal squared distance from points to their cluster centres. Lower is tighter.
LeakageInformation about the answer reaching the model through its inputs. Produces false accuracy.
Log-lossA score that punishes confident wrong answers. Lower is better.
NormalisationRescaling values to a common range.
OLAPOnline Analytical Processing — databases shaped for large read-only analytical queries.
One-hot encodingTurning a category into one 0/1 column per possible value.
OverfittingMemorising the training data rather than learning a pattern that generalises.
PCAPrincipal Component Analysis — projecting many dimensions onto the few with most spread.
ProtobufProtocol Buffers, a compact binary message format. Streamlit's wire format.
RerunStreamlit's model: every interaction executes the whole script again.
Silhouette score−1 to +1 measure of how well-separated clusters are.
StandardisationRescaling so mean is 0 and standard deviation is 1.
Star schemaOne fact table joined to several dimension tables.
Supervised learningLearning from examples that have the right answer attached.
Surrogate keyAn artificial integer identifier, used instead of a natural key like a name.
Unsupervised learningFinding structure in data with no answers provided.
WebSocketA persistent two-way connection between browser and server.
Window functionSQL that computes across a set of rows related to the current one — e.g. ROW_NUMBER() OVER (PARTITION BY …).
